# Differences between the arm64 and x86_64 builds that have been looked at.
# Anything not listed here fails the run; a row here that has stopped differing also fails,
# because a stale entry is worse than none.
#
# A row in this file records THAT the two architectures differ and what each one computes.
# It does not say which is correct. That question is "what does the Windows build do", and this
# machine cannot answer it - see the header of run_arch_diff.sh.
#
# section<TAB>key<TAB>arm64<TAB>x86_64<TAB>note

# --- float-to-long conversion, out of range ------------------------------------------------
# arm64's FCVTNS saturates to the destination's bounds. x86's cvtss2si/cvtsd2si does not: it
# yields the "integer indefinite" value 0x80000000 for anything it cannot represent, including
# NaN and the infinities. Both are documented, architecture-defined behaviour.
#
# Recorded as of B3's DetRound.h, whose comment covers the saturation case and not the NaN one.
# Reported to B3 as B12's finding; not adjudicated here. The callers are frame numbers, scanline
# coordinates and pixel counts, so no caller is currently believed to reach these inputs.
convert	f32/pos-2^31	2147483647	-2147483648	FCVTNS saturates; cvtss2si gives 0x80000000
convert	f32/1e10	2147483647	-2147483648	FCVTNS saturates; cvtss2si gives 0x80000000
convert	f32/+inf	2147483647	-2147483648	FCVTNS saturates; cvtss2si gives 0x80000000
convert	f32/nan	0	-2147483648	FCVTNS gives 0 for NaN; cvtss2si gives 0x80000000

# --- the same, for doubles, plus the width of `long` ---------------------------------------
# These rows differ for a second and larger reason. The arm64 path converts with a 64-bit
# instruction into a 64-bit `long`, so it does not narrow to int32 at all, while cvtsd2si is a
# 32-bit conversion. Note what that means for reading this table: `long` is 64 bits on BOTH
# targets here and 32 bits on Windows, so the x86_64 column is not a Windows answer either. It
# happens to coincide because cvtsd2si is 32-bit regardless of the type it is assigned to.
convert	f64/pos-2^31	2147483648	-2147483648	64-bit convert into 64-bit long vs 32-bit cvtsd2si
convert	f64/1e10	10000000000	-2147483648	64-bit convert into 64-bit long vs 32-bit cvtsd2si
convert	f64/-1e10	-10000000000	-2147483648	64-bit convert into 64-bit long vs 32-bit cvtsd2si
convert	f64/big-exact	4503599627370496	-2147483648	64-bit convert into 64-bit long vs 32-bit cvtsd2si
convert	f64/big-odd	4503599627370497	-2147483648	64-bit convert into 64-bit long vs 32-bit cvtsd2si
convert	f64/+inf	9223372036854775807	-2147483648	FCVTNS saturates to int64 here; cvtsd2si gives 0x80000000
convert	f64/-inf	-9223372036854775808	-2147483648	FCVTNS saturates to int64 here; cvtsd2si gives 0x80000000
convert	f64/nan	0	-2147483648	FCVTNS gives 0 for NaN; cvtsd2si gives 0x80000000

# --- D3DXVec4Transform (B17), a NaN generated by inf * 0 --------------------------------------
# (1, 1, 1, inf) through the Bezier basis: lanes y, z and w each multiply w = inf by a zero entry,
# which generates a NaN, and the two architectures generate different ones. x86 produces the
# "QNaN floating-point indefinite" 0xFFC00000; arm64 produces the default NaN 0x7FC00000. Both
# are architecture-defined, and C has no way to choose. Microsoft's DLL is x86 code, so the
# Windows answer is the x86_64 column, and a Mac build disagrees with it here. Accepted: an
# infinite shell coordinate means the simulation has diverged already, and d3dxportable.h says
# so. Lane x has no zero entry to multiply, gives +inf on both, and is not listed.
d3dx	inf-w/y	0x7fc00000	0xffc00000	inf*0: arm64 default NaN vs x86 QNaN indefinite
d3dx	inf-w/z	0x7fc00000	0xffc00000	inf*0: arm64 default NaN vs x86 QNaN indefinite
d3dx	inf-w/w	0x7fc00000	0xffc00000	inf*0: arm64 default NaN vs x86 QNaN indefinite
